# 写作材料的储存与管理（作者视角流程走查）

> 本文回答：作为作者实际使用这套 skills 时，每一份材料存在哪、谁来管、怎么找回来。
> 走查暴露的 v0.2 缺口以 ⚠ 标注，修正已并入本文。

## 一、总原则

1. **skills 与作品分仓**。⚠ v0.2 未定。skills 是全局工具（一个公开或私有的 skills 仓库，
   装进 Claude Code）；**每部作品是独立的私有 git 仓库**——独立历史、独立权限，
   写作材料永远不和工具代码混在一起。
2. **正文是唯一事实源**，圣经和账本是它的**索引**。索引服务两个目的：
   人查得快，AI 不必把全部正文读进上下文。
3. **git 对作者透明**。⚠ 新增。作者不需要学 git：每次写作会话结束由 skill 自动提交
   （提交信息=章节+日期+一句话摘要），大修前自动打标签。作者的心智模型是
   "每天的稿子都有存档，随时能回到任何一天"，而不是 commit/branch/rebase。
4. **一切材料都能回流**。⚠ 新增。作者不会只在会话里写作——手机备忘录里的灵感、
   Word 里手写的一段、朋友的反馈，丢进对应目录后由收割统一入册。
   体系不假设所有字都产生于会话之内。

## 二、一部作品的完整目录（v0.2 修订版）

```
<作品名>/                    # 独立私有仓库
├── bible/                   # 圣经：正文的索引，不是设定百科
│   ├── premise.md           # 前提、主题、类型承诺
│   ├── characters/          # 一人一文件；每条事实带出处（"灰眼睛（第3章）"）
│   ├── world.md             # 世界规则；硬规则单列（违反=bug）
│   └── timeline.md          # 大事年表（章节⇄故事内时间对照）
├── ledger/
│   ├── promises.md          # 工作账本：只放未兑现的承诺（保持短！）
│   └── promises-archive.md  # ⚠ 新增：已兑现/已打破的归档，防账本膨胀
├── outline.md               # 仅大纲式维度存在
├── manuscript/
│   ├── v1/                  # 卷（或"第一部"）
│   │   ├── 001-雪夜.md      # 一章一文件，三位数字保证排序
│   │   └── 002-灰市.md
│   └── handoff.md           # 交接文档：上次写到哪、下一场意图（每次会话末更新）
├── cut/                     # ⚠ 新增：废稿堆。删除的场景移入此处，永不真删
│                            #   ——心理安全感 + 素材可复用，且收割不扫描此目录
├── notes/
│   ├── inbox.md             # ⚠ 新增：灵感收件箱，随手丢，无格式要求
│   └── fragments.md         # 碎片堆（explore 产物，金句/画面/半个想法）
└── research/                # ⚠ 新增：外部资料（摘录、参考、图片），只读素材区
```

## 三、每份材料：谁写、谁读、何时动

| 材料 | 谁写入 | 谁消费 | 管理动作 |
|---|---|---|---|
| 正文 manuscript/ | /write（作者可随时手改） | 读者；收割扫描 | 会话末自动提交 |
| 圣经 bible/ | 大纲式：/develop 事前建；发现式：收割事后长 | /write 写前加载摘要 | 与正文冲突时作者裁决 |
| 工作账本 promises.md | 收割 | /write（每场必读） | 兑现即移入归档 |
| 交接 handoff.md | 每次会话结束 | 下次会话开头 | 覆盖式更新，不累积 |
| 收件箱 inbox.md | 作者随手丢 | /develop 定期清理：碎片归 fragments、设定归圣经、废弃划掉 | 清空是常态 |
| 废稿 cut/ | /write、/revise 删场景时 | 作者想捞回时 | 只进不出，除非复用 |
| 资料 research/ | 作者或 /research 类 skill | /develop、/write 按需引用 | 只读 |

## 四、上下文预算：目录结构存在的真正理由

⚠ v0.2 隐含未言明，此处明确。写第 30 章时**绝不**把前 29 章读进上下文。
`/write` 开工时加载的是固定的一小篮：

1. `handoff.md`（上次写到哪、这次写什么）
2. `bible/` 中与本场出场人物、地点相关的条目（不是全圣经）
3. `promises.md` 工作账本（因为只放未兑现项，所以永远不大）
4. 前一章（或前一场）的**结尾**若干段——衔接语气用
5. 大纲式：outline.md 中本场的条目

其余一切（全量正文、归档账本、废稿、资料）都在磁盘上等着被按需检索。
**目录结构就是上下文管理策略**：文件切得对，加载才能小而准。

## 五、作者的四个典型日子（流程走查）

### 第 0 天：开坑
`/setup-story` → 三维度光谱访谈 + 类型承诺 → 生成目录，git 仓库初始化，首次提交。
发现式作者此时的 bible/ 几乎是空的——这是特性不是缺陷。

### 日常：发现式的一个写作日
1. 开新会话。skill 读 handoff + 账本 + 上章结尾（半分钟内恢复记忆）。
2. `/write`：从"人物此刻想要什么"直接向前写。作者与 AI 逐段协作，
   作者随手改过的段落以磁盘版本为准。
3. 写完一章 → **收割**自动运行：新设定入圣经（注明"第 N 章"出处）、
   新承诺入账本、冲突即报告。
4. 会话结束：更新 handoff → 自动提交 → 推送备份。作者全程没碰过 git。

### 日常：大纲式的一个写作日
同上，仅第 2 步不同：从 outline.md 取下一场，写前先答两问——
本场推进哪条承诺？结束时什么值变了？

### 三周后回坑 / 第 30 章查设定
回坑：开会话读 handoff 即恢复，长断更靠"重读上一章全文 + 账本"补感觉。
查设定（"那个配角眼睛什么颜色？"）：先查圣经（索引带出处），圣经没有则 grep 正文
——查到后顺手补进圣经，索引越用越全。

### 大修
修订前自动打标签（"v1-初稿完成"），作者说"回到初稿"即可恢复任何标签版本。
修订产生的删除场景进 cut/，修订后重跑收割核对账本。

## 六、走查后仍开放的问题

1. 收割粒度：按场还是按章（当前推荐：按章，连载可配置）。
2. 发现式 /write 的写前仪式：零仪式 vs 一句话意图确认。
3. characters/ 条目的格式：自由 prose vs 轻结构（欲望/恐惧/滑尺/语言习惯四栏）——
   倾向轻结构但允许 prose 区。
4. research/ 是否需要引用机制（正文某设定源自某资料）——M1 不做，观察需求。
